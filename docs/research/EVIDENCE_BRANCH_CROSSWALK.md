## 5. Preserved branch-specific findings

### Branch A findings that must not disappear

- Eight explicit route records and fifteen capability-family records were created in its acquisition comparison.
- Coresignal Company Posts and Multi-Source Company products are distinct leads; daily delivery for one product is not proof of daily native publication capture for another.
- Bright Data's remote job lifecycle and per-input failure semantics require job receipts/reconciliation; retrying a lost POST can create a second paid job unless idempotency/reconciliation is established.
- Public-page implementations can preserve stale prior output and rewrite generation metadata, so output freshness cannot be equated with source freshness.
- Derived/relative timestamps and convenient author fallbacks cannot become native facts without validation.
- Company-updates prior art reproduced partial-result loss, duplicates, budget ambiguity and zero synthesis under fake transports.
- Retention expiry and source deletion are different events; policy-carrying evidence/derivative handling is load-bearing.
- Branch A's selected T17 expiry/replay experiment is still useful and not performed.

### Branch B findings that must not disappear

- Evidence/intake model distinguishes occurrence, representation/content version, observation, delivery and acquisition lineage; latest-only is not lossless history.
- Provider receipt identity can differ from projected-data identity; provider receipt time is not source observation time.
- Copied upstream classifier rules contain false-positive/overbroad possibilities under synthetic cases; source authors themselves said some security response shapes were uncaptured.
- A body-read exception can disappear at a selected request interface; later parser behavior must not be assumed from `{ok:true}` at that layer.
- A preflight-to-fetch interval exists in copied control flow; logical gate tests do not prove physical no-dispatch.
- The first local stop model actually failed a same-task/new-account reassignment probe after 44 green tests; task holds were added and the final 47 passed.
- Rate/challenge/session/task/route reasons must not silently clear one another; acknowledgements need exact reason/revision and actual production authentication.
- The actual M2 evidence intake is the next high-value source-inspection target in Branch B.

## 6. Apparent conflicts that are not true contradictions

### Official retention numbers

Branch A and B cite different durations because they examined different programs/field classes. Treat each rule as route/program/field-specific. Never derive one universal "LinkedIn retention period."

### Providers

Different provider lists reflect different research choices, not disagreement. The merged landscape contains all of them.

### Next operation

Branch A chose T17 because retention was its newest load-bearing discovery. Branch B chose M2 source inspection because response/stop semantics had just been tested. Once Codex has real source/runtime access, actual M1/M2 boundary + current live acquisition evidence outrank another purely synthetic pass.

## 7. True unresolved tensions

1. **Relationship/network scope:** Branch A excludes person-enumeration/private graphs; Branch B keeps account-scoped relationship views as a potential surface. Production scope should remain bounded, read-only and evidence-relevant; no mass/private graph collection.
2. **Current private-web route validity:** several historical/current-ish implementations exist, but neither branch captured a current authorized production response. This is an empirical gap, not a documentation argument.
3. **M1 ordered-history interface:** both branches preserve a document-reported mismatch; actual source/deployment verification is required.
4. **Candidate vs approved recipe execution:** project docs differ in wording; actual planner/router code must resolve the boundary.
5. **Source time/identity/reshare semantics:** many candidates exist, no current genuine fixture closes them.
6. **Retention/rights:** public visibility or technical access is not sufficient evidence of allowed recurring archival use.
7. **Physical stop fence:** Branch B's local gate is not a distributed dispatch guarantee.

## 8. What Codex should consider "already researched enough"

Do not spend the first implementation passes creating another generic survey of:

- whether LinkedIn has Voyager/Rest.li/GraphQL-like web-client surfaces;
- whether open-source LinkedIn collectors exist;
- whether provider APIs exist;
- whether normalized responses can contain referenced/included entities;
- whether provider timestamps/provenance can differ from native source time;
- whether old collectors can mishandle pagination/partial results;
- whether source challenges/rate limits require conservative stop behavior.

Those points are already supported enough to move to current code/live verification. Research again only when needed to resolve a specific implementation decision.
